# Spec: The real backend (Supabase + AI Gateway behind the existing app)

Status: ready-for-agent

**Scope:** replace the mock, browser-only data layer with a real backend, behind
the screens and flows that already exist. Covers the whole backend, sequenced
critical-path-first: (1) real auth + shared database + cross-device Handover,
(2) AI generation, (3) web push + reminders, (4) pilot analytics.
**Respects:** ADR-0002 (single mode flag), ADR-0003 (link-as-access),
ADR-0004 (Access requires an Account), ADR-0005 (Find Care stays referral-only),
ADR-0006 (revoke ends Access but retains a private Past Caregiver),
ADR-0007 (one Caregiver per pet).
**Glossary:** uses `CONTEXT.md` terms throughout: Account, Diary, Membership,
Owner, Caregiver, Access, Handover link, Referral code, Feeding confirm, Circle,
Past Caregiver, Rating; Site terms Home, Waitlist mode, Live mode, Sign-in.
**Seams:** the single `diary-service` seam stays the primary boundary (it goes
async, Supabase + AI Gateway backed); two small dedicated seams are added for the
reminder scheduler and for analytics.

## Problem Statement

Everything in the app works, but only on my own device, and none of it is real.
When I hand my pet's Handover link to a sitter, they open it on their phone and
see nothing, and the Diary lives only in the browser I created it in. If I switch
devices or clear my browser, my pet's Diary is gone. My diet plan and grooming
guide are canned rather than tailored to my pet. I never actually get a reminder
when I forget to log a Feeding confirm. And the team running the pilot cannot see
whether any of this is landing. To run the pilot, the same app needs a real
backend behind it.

## Solution

Keep every screen exactly as it is, and put a real backend behind them. I sign in
for real with an email magic link or Google. My Diary lives in the cloud, so it is
the same on every device and survives a browser wipe. When I share my pet, a
sitter on any device sees the full Diary read-only with no account; when I revoke,
their Access stops immediately, and I keep a private Past Caregiver record of them.
My diet plan and grooming guide are generated by AI from my pet's details, with the
safety guardrails, and I can still write them myself if I want. I can opt into push
reminders and actually receive them, and declining never blocks anything. And the
pilot's key moments are measured so the team can see what the pilot proved.

## User Stories

### Identity and account
1. As a new Owner, I want to sign in with a magic link sent to my email, so that I can start without a password.
2. As a new Owner, I want to sign in with Google, so that I can start in one tap.
3. As a returning Owner, I want to land back in my Account on any device, so that my Diary is always there.
4. As an Owner, I want my identity to be the same across every device, so that my Diary, Circle, and history follow me.

### Persistence
5. As an Owner, I want my Diary (name, species, breed, age, weight, photo, quirks, vet, rabies) stored in the cloud, so that it survives a browser wipe and is identical on every device.
6. As an Owner, I want my Feeding confirms and their history saved server-side, so that my log is complete and shared across devices.
7. As an Owner, I want my diet plan and grooming guide saved to my Diary, so that I can reopen them anytime, on any device.
8. As an Owner, I want my Circle, my Ratings, and my Past Caregiver records stored privately server-side, so that only I can see them.

### Handover across devices (the load-bearing change)
9. As an Owner, I want to generate a Handover link that anyone can open on their own device, with no account, and see my full Diary read-only (ADR-0003).
10. As a sitter with no Account, I want to open the Handover link on my own phone and see the Diary, so that I can care for the pet without signing up.
11. As an Owner, I want to see who currently has Access via the link, so that I know who can see my pet.
12. As an Owner, I want to revoke the link and have Access stop immediately on every device, so that I stay in control of who sees my pet.
13. As an Owner, after I revoke, I want the person retained as a private Past Caregiver (ADR-0006), so that my Circle remembers them.
14. As an Owner, I want to generate a fresh Handover link after revoking, so that I can re-share safely.

### Caregiver
15. As a sitter viewing via the link, I want to sign up and be bound to that specific Diary as a Caregiver (ADR-0004), so that I can log a Feeding confirm and opt into reminders (but not gain Owner rights).
16. As a Caregiver, I want to be the single Caregiver bound to the pet (ADR-0007), so that responsibility is unambiguous.
17. As a Caregiver, I want my Access to end the moment the Owner revokes (ADR-0006), so that the Owner stays in control.

### AI generation
18. As an Owner, I want my diet plan generated by AI from my pet's breed, age, weight, and current food, with the non-blocking disclaimer, so that it is tailored, not canned.
19. As an Owner, I want my grooming guide generated by AI from my pet's breed and coat type, with a recommended frequency, so that it fits my pet.
20. As an Owner, I want the AI diet plan to respect the product's safety guardrails (vet-constrained, never a prescription diet), so that I am never handed unsafe advice.
21. As an Owner, I want to write the plan or guide myself if the AI is unavailable, so that I am never blocked by a backend outage.

### Reminders and push
22. As an Owner, I want to opt into push notifications, so that I can get reminders.
23. As an Owner, I want a feeding reminder when no Feeding confirm has been logged for the day, so that I do not forget.
24. As an Owner or Caregiver, I want a grooming reminder on the guide's schedule, so that I keep the rhythm.
25. As an Owner, I want to decline notifications and keep using the app fully, so that reminders are never a wall (no-guilt hard rail).

### Measurement
26. As the team, I want the five pilot events captured (diet plan generated, diet plan viewed, daily Feeding tap, Handover link created, Handover link opened by recipient), so that we can measure the pilot.
27. As the team, I want each event mapped to one of the four belief statements in a viewable report, so that we can tell what the pilot proved.

### Privacy and continuity
28. As an Owner, I want my data scoped to me and my Circle, and revocation enforced by the server, so that sharing is genuinely safe (privacy hard rail).
29. As an Owner, I want the exact same screens and flows I have today, so that nothing I already know changes.

## Implementation Decisions

- **Provider.** Supabase for Auth, Postgres, and Storage; an AI Gateway for generation. This is what the `diary-service` header comments already anticipate ("Supabase queries + AI Gateway calls").
- **Primary seam stays `diary-service`, but goes async.** The exported function *shapes* are preserved; every function becomes Promise-returning and is backed by Supabase queries instead of `localStorage`. This is the largest mechanical change: every call site must `await`. It is a wide refactor and should be run as expand-contract (add the async form beside the sync one, migrate call sites in batches, then remove the sync form), not a single tracer bullet.
- **Auth.** Supabase Auth with email magic link and Google OAuth. `getAccount()` reads the Supabase session; the mock `signIn(email)` and the hardcoded `you@pouncity.app` are removed. Access requires an Account (ADR-0004).
- **Database (Postgres).** Tables for `account`, `diary`, `membership`, `feeding_entry`, `handover_token`, `past_caregiver`, `rating`, plus reminder/push subscriptions and an analytics `event` store; diet plan and grooming guide persist on the Diary (JSON) or their own tables. Row-level security scopes reads: an Owner sees only their own Diaries and Circle; a Caregiver sees only Diaries they are bound to; the public Handover route reads by token with no session. One Caregiver per pet is enforced at the database (ADR-0007).
- **Handover endpoint (the seam that could not exist client-side).** A public server route resolves a Diary read-only by Handover token from the database, with no session required. `resolvePublicDiary(token)` and `registerHandoverOpen(token)` become calls to that route. Revoking flips the token's state server-side so the route returns nothing immediately on every device (ADR-0003 link-as-access; ADR-0006 retains a Past Caregiver on revoke).
- **AI generation, server-side.** `requestDietPlan` and `requestGroomingGuide` call the AI Gateway from the server (keys never reach the client), apply the diet guardrails before returning, and save the result to the Diary with the disclaimer. The existing deterministic templated generators and the manual `saveDietPlan` / `saveGroomingGuide` paths are kept as the fallback when the AI Gateway is unavailable, so a core screen never hard-depends on the model.
- **Reminders and push (separate seam).** A service worker plus Web Push (VAPID). The client subscription rides the existing reminder opt-in (`setFeedReminderFor` and the grooming reminder flag). A scheduled server job (cron) evaluates, for each Diary with reminders on, whether a Feeding confirm exists for the day and sends the feeding reminder, and sends grooming reminders on the guide's schedule. The scheduler is a distinct, time-triggered, server-only seam. Declining notifications never blocks any feature (no-guilt hard rail).
- **Analytics (separate seam).** A thin `lib/analytics.ts` `track(event, props)` boundary emits the five pilot events to an event store, plus a report that maps each event to one of the four belief statements. Kept out of `diary-service` because it is cross-cutting.
- **Runtime and mode.** The app moves from a browser-only build to actually using its server routes, with secrets in the production environment (Supabase URL and keys, AI Gateway key, VAPID keys, analytics token), deployed separately from the current preview. The Live-mode / Waitlist-mode flag (ADR-0002) governs what is public; production stays Waitlist-mode until Live mode is flipped.
- **Sequencing (critical path first).** (1) auth + database + cross-device Handover, which alone makes the app genuinely multi-device and real; (2) AI generation; (3) push + scheduler; (4) analytics.

## Testing Decisions

- **A good test checks external behavior at a seam, not implementation.** Prior art: the existing in-browser behavior checks against the mock `diary-service`, and the seam-level tests already used for the owner-app work.
- **Primary seam, `diary-service` (async).** Against a test Supabase project (or a seam-level fake), assert: a fresh Account creates a Diary and it persists; a second client for the same Account (a "second device") sees that Diary; a Feeding confirm made on one client is visible on another. These are the cross-device guarantees the mock could never make.
- **Handover seam, the public route (highest value).** A client with no session opens a valid token and receives the Diary read-only; after the Owner revokes, the same token returns nothing; multiple independent clients open the same token successfully. Test across separate storage contexts so "another device" is real, not simulated in one browser.
- **AI seam, `requestDietPlan` / `requestGroomingGuide`.** With a stubbed AI Gateway response (deterministic, never the live model in tests): a generated plan/guide is saved with the disclaimer; an unsafe suggestion is rejected or constrained by the guardrail; the manual fallback path still saves a plan when generation is unavailable.
- **Reminder seam, the scheduler evaluation.** Given a Diary with reminders on and no Feeding confirm for the day, the evaluation yields a send; given a confirm, it yields none; grooming yields a send on schedule. Test the pure evaluation function directly, separate from actual push delivery.
- **Analytics seam, `track`.** Each of the five events fires per its rule (daily tap once per day per Diary; handover-opened once per unique recipient); each event maps to a belief. Test the `track` boundary, not the analytics vendor.
- **Authorization / RLS at the data boundary.** An Owner cannot read another Owner's Diary; a Caregiver reads only Diaries they are bound to; the public route serves only a valid, unrevoked token.

## Out of Scope

- The Find Care marketplace and stranger discovery. Find Care stays referral-only (ADR-0005).
- Any change to screens, flows, copy, or the domain model. This is a backend swap behind the existing UI.
- The marketing Site and Waitlist. Production stays Waitlist-mode until Live mode is flipped (ADR-0002).
- Multiple Caregivers per pet (ADR-0007 keeps one), payments, and native apps / native push (web push only for the pilot).

## Further Notes

- **The sync-to-async seam change is the biggest mechanical risk** and touches every call site; run it as expand-contract, not a tracer bullet.
- **One decision to settle before wiring the AI Gateway:** the pilot ticket breakdown says "disclaimer only; no diagnosed-condition question blocks generation," which sits against the product hard rail that the AI must vet-constrain the diet and never suggest a prescription diet. Choose the guardrail model (disclaimer-only vs an actual constraint layer) first.
- **The built app already leads the pilot docx** (Circle, Rating, Past Caregiver, handover-readiness gate, one-Caregiver-per-pet). The backend should implement this richer model, not the thinner docx version.
- **Privacy is a hard rail:** scope and revocation must be enforced by the server (row-level security plus token state), never only honored in the Owner's browser.
- The templated generators and manual save paths stay as graceful fallback, so a core screen is never blocked by an AI Gateway outage.
